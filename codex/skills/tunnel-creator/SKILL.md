# Tunnel Creator — воронки в Leeloo.ai

Збірка воронок через MCP `leeloo-mcp` (сервери leeloo-dev / leeloo-stage).

Головне, що варто засвоїти одразу: **API вміє більше, ніж описує `get_vocabulary`,
і місцями цей опис прямо помилковий.** Розділ «Пастки API» нижче — не довідка на
всяк випадок, а перелік місць, де без попередження губиться година.

---

## Порядок роботи

```
1. Прочитати джерело схеми → 2. Спека → 3. Узгодити 3 рішення → 4. Збірка → 5. Валідація
```

**Не створюй блоки, доки не маєш повного тексту повідомлень.** Тунель на 80
блоків із вигаданими текстами доведеться перебирати руками — це дорожче за
пʼять хвилин уточнень.

### 1. Джерело схеми

- **Miro** — `context_explore` / `context_get`. Якщо `Board access denied`, не
  шукай обхідних шляхів: попроси скріншоти або доступ.
- **Скріншоти** — читай дослівно. Обрізані рядки лишай обрізаними й винось у
  список питань.
- **Опис словами** — перепитай про блоки, кнопки, теги, тайминг.

### 2. Спека

Проміжний артефакт між джерелом і збіркою. Один розділ на блок:

```markdown
### D3.2 · MSG «Модуль 1» 🎥
> Вітаю 🎉
> Доступ до модулю 1 відкрито

**Кнопки (LINK):** Урок 1 · Урок 2 · Домашнє завдання
**Тег:** Модуль 1   **Час:** день 7, 10:00
```

Емодзі в назві позначають медіа, якого ще немає: 🎥 кружечок, 🖼 фото, 📹 відео.
Наприкінці — розділ «Що потрібно від замовника»: обрізані тексти, відсутні URL,
медіа. Спека дає одне джерело правди і дозволяє паралелити збірку.

### 3. Три рішення, які питай ДО збірки

| Питання | Чому важливо |
|---|---|
| Тайминг: відносні затримки чи фіксовані дати? | Змінює тип усіх DELAY. Дати зі старих схем зазвичай уже минули. |
| Медіа: чекати файли чи будувати каркас? | Каркас із плейсхолдерами дає результат зараз. |
| Куди ведуть цільові кнопки? | Оффер, тег, лендінг чи менеджер — різні типи кнопок. |

### 4. Збірка

1. `get_vocabulary` — статичний, мережу не смикає
2. `list_connections`, `list_tags`, `list_custom_fields` — розвідка оточення
3. `create_tunnel` → порожній тунель з одним MESSAGE_BLOCK
4. `create_tag`, `create_custom_field` — знадобляться в діях
5. **Створити всі блоки без звʼязків**, потім **звʼязати гуртом** `create_relation`
6. Наповнити контентом (`update_block_*`)
7. `layout_tunnel` → `validate_tunnel`

Крок 5 у два проходи не з примхи: `create_block` вміє малювати ребро одразу через
`parent_blocks`, але тоді кожен блок залежить від попереднього і паралелити
неможливо. Пачка блоків + пачка ребер скорочує десятки послідовних раундів до кількох.

### 5. Валідація

Нуль `errors` = можна комітити. Попередження `UNREACHABLE_BLOCK` часто
легітимне — див. «Пастки» §7.

## Модель: як усе зʼєднано

**Блоки зʼєднуються рядками в колекції Relations, а не полем `parent_blocks`.**
Редактор малює лінію тільки там, де є relation. `parent_blocks` і
`conditional_children` — легасі, у редакторі невидимі.

```
TUNNEL_BLOCKS        from_tunnel_block_id → to_tunnel_block_id
                     TUNNEL_BLOCK_PASS (звичайний перехід)
                     DELAY_SUCCEED | FILTER_SUCCEED | FILTER_FAILED | TRIGGER_*

BUTTON_TUNNEL_BLOCK  from_button_id → to_tunnel_block_id
                     BUTTON_PASS
```

**Кнопка сама по собі нікуди не веде.** Три кроки, жоден не пропускається:

```
1. create_button   type, connection_type, name, data, tunnel_block_id
2. покласти id у buttons[] елемента e-text   (update_block_message)
3. create_relation BUTTON_TUNNEL_BLOCK, BUTTON_PASS
```

Пропустив крок 2 — кнопки не видно. Пропустив крок 3 — видима, але мертва.

### Формат повідомлення

```json
{ "block_id": "...", "tunnel_id": "...",
  "message": { "content_telegram": [
    { "class": "e-text", "text": "Текст", "buttons": ["<button_id>"] }
  ]}}
```

Кілька `e-text` = кілька окремих повідомлень підряд. Класи обмежені каналом:
`e-video-note` (кружечок) і `e-media-group` існують **тільки в Telegram**. Клас
не з того каналу пройде валідацію, збережеться і мовчки не відправиться.

### Затримки

```json
{ "type": "WITH_DELAY", "delay_in_seconds": 300 }
```

Привʼязка до годинника — `WITH_DELAY_IN_ALLOWED_TIME`: чекає N секунд, але
доставляє лише у вікно доби.

```json
{ "type": "WITH_DELAY_IN_ALLOWED_TIME", "delay_in_seconds": 43200,
  "allowed_from_in_seconds": 36000, "allowed_to_in_seconds": 39600,
  "allowed_days_of_week": ["MON","TUE","WED","THU","FRI","SAT","SUN"],
  "time_zone": 3 }
```

Секунди від опівночі: `години*3600 + хвилини*60`. 09:45=35100, 18:00=64800,
19:20=69600, 21:10=76200.

`ON_DATE` з `send_date` — лише під конкретний запуск, для багаторазової воронки не бери.

**Підводний камінь відносних затримок:** відлік іде від моменту, коли людина
дійшла до блоку. Підписався о 23:00 — ланцюжок «+1 день, вікно 10:00» зсунеться
на добу. Це властивість моделі, а не баг; рішення за користувачем.

### Теги і фільтри

```json
update_block_action({ actions: [{ "type": "ADD_TAGS", "tags": ["<tag_id>"] }] })
```

Імена тегів унікальні в межах компанії (дубль → 400 `NAME_ALREADY_IN_USE`).
Іменуй з префіксом проєкту: `FT: Бронь місця`. Без префікса у компанії з
десятками воронок теги перетворюються на кашу.

FILTER маршрутизує за обʼєктом person-filter — скаляр чи масив дадуть 400
`FORMAT_ERROR`:

```json
{ "tags": ["<id>"], "reverse_tags": false }
```

Ключі: `tags`, `tunnels`, `leadgentools`, `connections`, `offers_opened`,
`offers_resolved`. Кожен має пару `reverse_*`. На виході дві гілки:
`FILTER_SUCCEED` і `FILTER_FAILED`.

## Патерни

### Ланцюжок нагадувань

```
Анонс → ⏱18:00 → «за годину» → ⏱18:30 → «за 30 хв»
      → ⏱18:55 → «стартуємо» → ⏱19:20 → «вже 200 учнів»
```

Вікна тримай вузькими (18:00–18:30), інакше «за 30 хвилин» прийде через дві
години після ефіру.

### Анкета

**Одне питання = один блок.** Спокуса скласти шість `e-request-info` в один блок
велика, але потім майже завжди просять розділити — щоб на кожне питання повісити
свою гілку «не відповів» і свій вхід.

```json
{ "class": "e-request-info",
  "text": "Як Вас звати?",
  "content_type": "KEYWORD",
  "button_text": "Відповісти",
  "success_message_text": "Приємно познайомитись 🤝",
  "error_message_text": "Напишіть, будь ласка, імʼя текстом 👇",
  "save_to_custom_field_id": "<field_id>",
  "time_to_wait_for_response": 900000,
  "actions": [{ "status": "EXPIRED", "type": "START",
                "tunnel_id": "<tunnel>", "tunnel_block_id": "<блок переуточнення>" }] }
```

`content_type` під зміст: `PHONE`, `NUMBER`, `EMAIL`, `DATE`, `KEYWORD` —
впливає на валідацію відповіді.

Щоб відповіді потрапляли в картку, потрібні кастомні поля (`create_custom_field`,
ліміт компанії 20, імена латиницею). Свій набір з префіксом (`ft_name`, `ft_phone`)
краще за перевикористання загальних полів — інакше дані різних воронок змішаються.

### Гілка «не відповів»

```
Q3 ──(EXPIRED через 15 хв)──▶ 🔵 «Без відповіді · Q3»
                                    │ кнопка «Повторно»
                                    └──────────▶ Q3
```

Кнопка «Повторно» має бути типу **SUBSCRIBE** і вказувати на LGT, привʼязаний до
блоку питання. FORWARD з relation тут не спрацює. Отже на кожне питання потрібен
свій LGT з `tunnel_block_id` = блок питання.

### Контекстний дожим

```
Продажний блок ──────────────────────────▶ (основний ланцюг далі)
      │
      └──▶ ⏱ 2 години ──▶ 🔍 Фільтр по тегу
                              ├── FILTER_SUCCEED → нікуди
                              └── FILTER_FAILED  → 🔥 Дожим
                                                      │ SUBSCRIBE
                                                      └──▶ назад у продажний блок
```

У продажного блоку **два вихідні ребра**. Існуюче не чіпай, додай друге.

Що покласти у фільтр — вибір із наслідками, проговори явно:

| Умова | Кого дожимає |
|---|---|
| `tags: [тег броні]` | Тег ставиться на **клік**. Хто клікнув і не оплатив — дожиму не отримає. |
| `offers_resolved: [offer_id]` | Тільки тих, хто **не оплатив**. Точніше для продажів. |

## Кнопки

| Тип | `data` | Нотатки |
|---|---|---|
| `FORWARD` | літерал `"FORWARD"` | Потрібна relation |
| `LINK` | URL | Може мати і URL, і relation |
| `BUY` | ObjectId офера | Відкриває оплату |
| `SUBSCRIBE` | **id traffic source**, НЕ id LGT | Словник помиляється — див. §1 |
| `PHONE_NUMBER` | номер | |
| `COMPLETE_PARTIAL` | `"CURRENT_ORDER"` або id | |
| `MESSAGE` | id template-message | **Через MCP не створюється.** Для переходів — FORWARD |

`MESSAGE` виглядає підхожим для переходу, але це «надіслати шаблон» (postback).
Id блоку в ньому пройде всі валідації й впаде вже у підписника з
`MESSAGE_FOR_POST_BACK_NOT_FOUND`.

Дійові кнопки (`LINK`, `BUY`) можуть мати **і дію, і relation** одночасно:
«Бронюю місце» відкриває оплату і паралельно веде на ACTION-блок з тегом —
менеджер бачить заявку, навіть якщо оплату не завершили.

**Заглушки:** коли URL ще немає, роби `FORWARD` без relation — кнопка видима,
клік безпечний. У назву блоку додай маркер `[URL?]`. `LINK` без URL впаде.

**Ліміти:** назва кнопки 20 символів, назва блоку 60, рядок 255.

## Офери

```json
create_offer({ "name": "Бронь", "price": 90, "currency": "USD", "language": "uk",
               "category_id": "<list_categories>",
               "payment_credits": ["<list_payment_credits>"] })
```

- **`currency` має бути увімкнена в компанії**, не просто існувати в ISO.
  Вимкнена дає непрозорий 500. Звіряй `supported_currencies` платіжки.
- **Не-GENERAL типи** (пакети, підписки) потребують дозволу; без нього бекенд
  мовчки понижує тип до GENERAL.
- `merchant_id` виду `pk_test_…` = **тестовий ключ**. Перед бойовим запуском
  обовʼязково скажи про це користувачу — легко запустити рекламу на воронку,
  де оплата не проходить.
- Прапорці `settings` часто вимагають парних полів у `additional_info`:
  `is_limited`→`in_stock`, `is_recurring`→`recurring_params`,
  `allow_partial_payments`→`percentage_of_*`.

Оффер живе окремо від тунелю: один оффер спокійно продається з пʼяти блоків.
Створюй раз і перевикористовуй.

Варто спитати: **ціна — це повна вартість чи передоплата?** Якщо передоплата,
потрібен `allow_partial_payments`, а не звичайний разовий оффер.

## LGT і міні-лендінги

Трирівнева модель, плутанина між рівнями коштує найбільше часу:

```
1. Запис LGT        create_leadgentool   ← сторінка, канали, traffic sources, URL
2. LEADGENTOOL-блок create_block + update_block_leadgentool   ← маркер на схемі
3. Потік нижче      create_relation
```

**Куди потрапляє підписник** визначає `tunnel_block_id` **самого запису LGT**, а
не позиція блоку. Передавай явно: попри опис інструмента, дефолт «перший блок»
не підставляється, лишається порожній рядок.

`set_first_block` — окрема історія: запасний вхід для прямого трафіку, тільки
MESSAGE_BLOCK. LEADGENTOOL туди не поставити, бекенд 404.

Типи: `link` (міні-лендінг з публічним URL), `button` (службовий, без сторінки —
ціль SUBSCRIBE-кнопки), `qr`, `widget`, `popup`, `form`, `smart-response`.

Фактично обовʼязковий лише `telegram.connection_id`. У відповіді забирай `id`,
`public_url`, `hash` і **`traffic_sources[0].id`**.

**Створення LGT метрується тарифом** — не плоди їх у циклі налагодження,
помилкові прибирай `delete_leadgentool`.

Блоки сторінки: `IMAGE{image}`, `TEXT{text}`, `CUSTOM{text=HTML}`,
`VIDEO{video_link,video_type,video_settings}`, `SUBSCRIBE{subscribe_button_name}`,
`FORM{custom_fields[]}`, `OFFER_BUTTON{offer_id}`. Чекбокси сторінки — це не
блоки, а прапорці в `settings`.

### HTML-блок: квізи

Пиши **фрагмент**: `<link>` + `<style>` + розмітка + `<script>`. Без `<!DOCTYPE>`,
`<html>`, `<body>`.

```css
.adaptive-container { top: -60px; }
* { margin: 0; padding: 0; box-sizing: border-box; }
.quiz-wrap { width: 100%; }   /* НЕ max-width */
```

**Не скоупь reset під власну обгортку** (`#myquiz * {...}`) і **не став
`max-width` з `margin: 0 auto`**. Контейнер Leeloo уже обмежений
`settings.lgt_width` (дефолт 450px); обмеження поверх нього стискає картку в
смужку. Це найчастіша причина «все зʼїхало».

**Кнопки месенджерів** — блок `.lgt-social-buttons.lgt-block`. У квізі його
ховають до фінального кроку через `body.final-step` + `MutationObserver`.

Пастка: типовий `hideFooter()` ховає все, у чиєму класі є
`footer`/`powered`/`privacy`/`policy`. Контейнер підписки містить блок згоди з
політикою — і потрапляє під роздачу разом із кнопками. Захист:

```js
if (el.classList && el.classList.contains('lgt-social-buttons')) return;
if (el.querySelector && el.querySelector('.lgt-social-buttons')) return;
```

На фінальному кроці **спершу зніми все приховування, потім переноси**. Навпаки —
і якщо перенос не вдасться, кнопки лишаться схованими назавжди. Плюс таймаут:
не знайшли за N спроб — лишаємо на місці, але видимими.

**Попередження «Відкрийте цю сторінку в вашому браузері»** Leeloo підставляє
замість кнопок у webview. Клас непередбачуваний — лови **за текстом**, вимагаючи
2+ збіги з фразами («відкрийте цю сторінку», «відкрити в браузері»,
«скопіювати посилання», RU/EN варіанти). Але чесно: якщо воно рендериться
**замість** кнопок, приховування лишить порожнє місце. Спершу перевір сторінку
у звичайному браузері окремою вкладкою — часто проблема тільки в прев'ю адмінки.

**Запис відповідей:**

```js
window.leeloo_additional_fields = {
  custom_fields: [{ name: 'ft_quiz', type: 'KEYWORD', value: summary }]
};
```

Поле має існувати заздалегідь. Стратегія «все одним рядком» простіша, але не
сегментується; окремі поля дають фільтрацію в CRM. Питай користувача і попередь:
якщо частина людей проходить анкету в боті, а частина через квіз, дані
опиняться в різних полях і зведення не вийде.

`localStorage` не використовувати — стан тримай у змінних JS.

## Пастки API

### 1. SUBSCRIBE: `data` — це traffic source

`get_vocabulary` каже `SUBSCRIBE: "the tunnel ObjectId"`. **Неправда.** І id
тунелю, і id LGT дають зламаний UI: `Cannot read properties of null (reading
'leadgentool_id')` і порожній селект «Select LGT».

Фронтенд робить приблизно `trafficSources.find(s => s.id === button.data).leadgentool_id`,
тобто шукає сутність із полем `leadgentool_id`. Така одна — traffic source.

```js
create_leadgentool({...})
// { id: "...c9f",                    ← НЕ це
//   traffic_sources: [{ id: "...ca9", ← ОСЬ це в data кнопки
//     leadgentool_id: "...c9f", resubscribe_button_id: "...caa" }] }
```

Якщо LGT створено раніше: кожен LGT автоматично отримує кнопку `RESUBSCRIBE`
(`resubscribe_button_id`), у якої в `data` вже лежить потрібний traffic source —
читай через `list_buttons`.

**Не вгадуй id арифметикою.** Id traffic source зазвичай іде відразу за id LGT,
але timestamp-префікс ObjectId відрізняється, якщо створення перетнуло межу
секунди. На шести LGT два id вгадались би неправильно.

### 2. `e-request-info`: реальний whitelist

Словник згадує 6 полів, бекенд приймає 14: `class`, `text`, `content_type`,
`button_text`, `success_message_text`, `error_message_text`,
`save_to_custom_field_id`, `actions`, `dont_save_response_to_card`,
`time_to_wait_for_response`, `is_silent`, `dont_forward_utms`, `dont_parse_links`,
`protect_content`.

`buttons` і `buttons_orientation` тут **не приймаються** (на відміну від `e-text`).

Поля «Повідомлення у разі відсутності відповіді», яке UI показує обовʼязковим,
**у моделі не існує** — перевірено ~160 кандидатів імен. Замість нього працює
EXPIRED-дія на окремий блок.

### 3. Гілка «не відповів» — через `actions`

Обидві UI-дії — це один масив всередині елемента:

```json
"actions": [
  { "status": "SUCCESS", "type": "START", "tunnel_id": "...", "tunnel_block_id": "..." },
  { "status": "EXPIRED", "type": "START", "tunnel_id": "...", "tunnel_block_id": "..." }
]
```

`status` приймає **рівно два** значення: `SUCCESS` | `EXPIRED`. `type` — **рівно
два**: `START` | `STOP`. `ADD_TAGS` тут не працює, це інший формат. Обидва
`tunnel_id` і `tunnel_block_id` обовʼязкові.

**Обережно з SUCCESS:** якщо основний перехід уже зроблено relations, не додавай
ще й `SUCCESS`-дію — людину просуне двічі.

### 4. Мовчазне відкидання полів

LIVR не лається на невідомі ключі — просто викидає. Успішна відповідь **не
означає**, що поле збереглося. Помилка приходить лише на *відоме* поле з поганим
значенням — і вона інформативна, часто містить enum допустимих.

Розвідка: записати пачку кандидатів одним запитом, потім прочитати обʼєкт і
подивитись, які вижили. **Після нетипового запису завжди перечитуй обʼєкт.**

### 5. `allowed_lateness_in_seconds` не персиститься

У `WITH_DELAY_IN_ALLOWED_TIME` приймається схемою, але завжди повертається
`null`. Вікно працює, «допустиме запізнення» — ні. Треба — виставляй у UI.

### 6. `update_*` замінюють цілі піддокументи

| Інструмент | Замінюється цілком |
|---|---|
| `update_block_message` | кожен переданий канал (інші збережуться) |
| `update_button` | **уся кнопка**: не передав `active` → стане `true` |
| `update_leadgentool` | `settings` цілком, `blocks` — повна заміна масиву |

Порядок: **прочитай → зміни потрібне → віддай усе назад.** Для LGT: міняєш
тільки `blocks` — **не передавай `settings` взагалі**, так вони збережуться самі.

### 7. `UNREACHABLE_BLOCK` — не завжди помилка

Досяжність рахується тільки по relations. Законно «недосяжні»: NOTE-блоки
(стікери), блоки-приймачі EXPIRED-дій (досяжні в рантаймі, але не через ребро).
LEADGENTOOL-блоки вважаються коренями входу і не репортяться.

Не малюй ребра, щоб «полагодити» попередження — зіпсуєш логіку. Поясни користувачу.

### 8. Медіа: URL, а не байти

Три шляхи: файл на CDN → url як є; локальний → `upload_file` з base64;
`create_upload_url` + PUT у S3 — **у пісочниці не працює**, проксі ріже вихід у
мережу (`HTTP 403 from proxy after CONNECT`). Не витрачай час, іди через base64.

Base64 великого файлу не влазить у ліміт виводу bash. Стискай перед заливкою
(`ffmpeg -i in.jpg -vf scale=1000:-1 -q:v 6 out.jpg`, ціль ~30–50 КБ для
лендінгової картинки) і роби це в субагенті, щоб блоб не осідав у головному контексті.

### 9. `401 SESSION_EXPIRED`

Токен OAuth протух. Ретраями не лікується. Скажи користувачу: вийти з застосунку
повністю (через трей, Quit), видалити теку `.mcp-auth` у домашньому каталозі,
запустити знову. Обхідних шляхів не вигадуй.

### 10. UI показує помилку, а API прийняв

Значить фронтенд читає інше поле. **Не гадай назви** — знайди в компанії
**робочий зразок** тієї ж сутності і подивись, що лежить у нього. Саме так
зʼясувалось, що SUBSCRIBE читає traffic source, а не LGT.

## Паралелення великих воронок

Воронка на 50+ блоків в один контекст не влазить: відповіді `create_block`
багатослівні (~700 токенів кожна), а `get_tunnel_graph` на сотні блоків — сотні
кілобайт, часто понад ліміт відповіді.

Розбий воронку на незалежні відрізки й віддай кожен субагенту:

- Спільні сутності (теги, блоки-приймачі гілок, LGT) створи **сам до** запуску
  агентів і передай готові id
- Кожен агент будує свій відрізок повністю: блоки, контент, кнопки, внутрішні ребра
- Кожен повертає **id входу і виходу** свого відрізка
- Ти зшиваєш відрізки трьома-чотирма `create_relation`

Напиши спільний файл-контекст (id тунелю, тегів, конвенції формату) і дай
посилання — дешевше, ніж дублювати інструкції в кожному промпті.

Шаблон промпту:

```
Завантаж інструменти: ToolSearch `select:mcp__leeloo-mcp__create_block,...`
Прочитай: <build-context.md>, <spec.md> розділ <який>
tunnel_id = <id>

## Правила
- Тексти дослівно зі спеки, нічого не переписувати
- update_block_message замінює канал цілком — передавай повний масив
- НЕ викликати layout_tunnel і validate_tunnel (це робота координатора)
- Нічого поза своїм діапазоном не чіпати
- Якщо 401 SESSION_EXPIRED — не шукати обхідних шляхів, повідомити
```

## Тексти

Тексти — це те, за що платить клієнт.

- **Дослівно з джерела**, включно з емодзі, помилками й лайкою. Не «покращуй».
- **Markdown зі спеки прибирай.** `**жирний**` у Telegram-елементі `e-text`
  покажеться зірочками. Виділення ставиться в редакторі.
- **Обрізане лишай обрізаним** і винось у питання до замовника. Дописаний
  «логічний кінець» фрази — найгірше: його ніхто не помітить, і він піде
  в бойову розсилку.
- **Чого в джерелі немає — вигадуй лише коли просять**, і чесно кажи про це
  у фінальному звіті.
